# 一个 SEO 的周末：把内容发布搬到 ZimaOS 之后，我终于睡上了好觉

## 先说我是谁

我是一名 SEO 从业者。日常就是找词、选题、写稿、改稿、发稿，然后盯着排名和收录看有没有起色。

我的一个主要阵地在自己的 Shopify 店铺博客上。做 SEO 的人都知道一件事：**内容要持续、要稳定、要像钟表一样准**。搜索爬虫不看你的心情，也不管你今天是不是在陪孩子。

而我最大的敌人是周六和周日。

## 那些让我睡不着的夜晚

以前我的发布流程很原始：

周一写好三篇稿子，做成 JSON，存在本地文件夹里；有空的时候打开浏览器，一篇一篇手动贴进 Shopify 后台，设置发布时间；忙起来就忘了；等想起来的时候，已经过了一周。

问题有三个，每一个都真实地折磨过我：

**第一，周末断更。** 周五晚上加班写完稿子，周六想休息，结果一想到"今天没有新内容"就心里发慌。周日更糟。SEO 是个慢变量游戏，断更两天不会立刻掉排名，但它会变成一种持续的心理负担 —— 你永远觉得自己欠着点什么。

**第二，人不在电脑前就发不了。** 出去旅游、回老家、用平板的时候，内容就卡住了。

**第三，也是最麻烦的：内容质量靠人眼守。** 我的博客里有好几个栏目，每个栏目的规则都不一样 —— 有的要求分级结构，有的对来源链接有前缀要求，有的主题模板必须精确匹配。手动粘贴的时候，把一篇该发到 A 栏目的文章发进了 B 栏目，或者 H2 数量不够，这些错误我犯过不止一次。**发错了比不发更糟**，因为你要么删掉（伤收录），要么留着（内容结构混乱）。

## 所以我写了一个工具

我给自己做了一个内容推送工具。它的逻辑很朴素：

1. **在本地写好 JSON**（标题、正文、meta、来源、关联产品……）
2. **打开工具，上传 JSON**，它先做一遍严格校验：栏目归属对不对、H2 够不够、来源链接前缀对不对、外链规则、主题模板是否在白名单里、图片 alt 有没有漏
3. **校验通过才允许发布**，可以选立即发布、定时发布、或者存成草稿
4. **定时用的是 Shopify 原生的发布计划** —— 这一点很关键，后面会讲

做完之后它的效果是这样：我周六早上打开它，看一眼未来两周的排期格子 —— 哪一天有内容、有几篇，一目了然。周一到周五写的内容，已经被排到了周末的固定时间点上。

**它不会漏发，因为到点发布这件事是 Shopify 自己做的，跟我的电脑开不开机没关系。**

这一条我想专门强调，因为它推翻了我最初的假设。我一开始以为"托管"意味着"服务器必须 7×24 小时不出问题"，还专门为此纠结了很久。实际上定时发布的任务一旦提交，就是在 Shopify 那边排队，我的服务器关一整天，内容照样准时上线。托管真正买到的不是"可靠性"，而是**"我随时能提交"**。

## 那为什么还要托管？

既然关机也不影响发布，为什么我不就在自己电脑上跑？

因为"必须打开电脑才能提交"这件事本身，就是我的痛点。我想：

- 在外面用平板也能上传一篇稿子
- 不用每次开两个终端窗口
- 打开浏览器就是一个固定地址，像用任何一个正规后台一样
- 家里那台一直开机的设备本来就在跑别的东西，顺手把它用起来

我家里的 NAS 是 ZimaCube，系统是 ZimaOS。

## 一个"小白"的真实水平

说清楚我的起点，后面的坑你才能理解为什么我会踩：

- **会跑服务，不会调服务。** 我用过 MySQL、Redis、Nginx —— 都是照文档配起来能跑就行，出问题会去搜报错。
- **Docker 只会最基础的。** 我理解"镜像"和"容器"的意思，但我的实际操作水平大概是：`docker run` 加几个参数，`docker ps` 看看活着没。
- **Compose、多阶段构建、镜像仓库、跨架构构建** —— 这些词我见过，没自己写过。
- **ZimaOS 我更是完全的新手。** App Store 里点过安装，但"自定义容器""自己加一个 compose"这种操作，我从没做过。

所以当我决定"把这个项目打包、放到 ZimaOS 上跑"的时候，我心里其实没底。

## 我是怎么做的：借助 DSH 把项目打包

我不会写 Dockerfile，所以我用 DSH（DeepSeek Harness）来做这件事。我把自己的 GitHub 项目交给它，说清楚我要什么：**一个镜像、一个端口、一个能一直跑的服务**。

它帮我做的事情里，有两件是当时的我根本想不到的：

**① 前端和后端放进同一个容器，同源。**

我原本以为要起两个服务（前端一个、后端一个），还要配反向代理。实际上把前端构建成静态文件、由后端顺带托管，只暴露一个端口就够了 —— 跨域问题直接消失，也不用碰 Nginx。对新人来说，**少一个组件就少一类事故**。

**② 凭据和配置完全不进镜像。**

镜像里只有代码，店铺凭据走环境变量，真实配置走文件挂载。这样镜像本身是"干净"的。

顺便说，这也让我后来做了一个正确的决定：**部署信息不要编译进镜像**。我最初的做法是让前端在构建时读取配置文件，结果发现构建出的镜像里带着我的域名和品牌 —— 想"用真实配置"和"镜像可以干净地给别人用"变成了两件互相排斥的事。后来改成让后端在响应页面时把配置注入进去，镜像就永远是通用版了，同一份镜像挂不同配置能服务不同站点。

这一点我觉得值得写给所有做自托管应用的人：**镜像负责功能，配置负责你是谁。** 混在一起，迟早会难受。

## 真正上 ZimaOS：我踩过的坑

下面这些是我实际踩到的，按我踩到的顺序写。如果你也是新手，希望你能少走一段。

### 坑 1：我以为"面板里粘一个 compose"就完事了

ZimaOS 的 App Store 支持自定义安装，可以把 compose 内容粘进去。我把配置写好、粘进去、点安装 —— **安装失败**。

面板只告诉我"安装失败"，没说原因。我是去翻设备日志才看到真相的：ZimaOS 在安装时会自己去拉镜像，而且**依次尝试了五个镜像源**，全部失败，最后报 `Failed to pull image: repository does not exist`。

我第一次学到了两件事：

- **面板安装时一定会去拉镜像。** 我在 compose 里写了"禁止拉取"，那个字段被忽略了。
- **"镜像就在本机 docker images 里"是不算数的** —— 它必须是一个**能被拉取**的名字。

### 坑 2：解法是我在设备上跑了一个本地镜像仓库

这个办法我现在觉得挺优雅的：既然面板要求镜像可拉取，那就在设备上放一个镜像仓库，把我的镜像推成 `localhost:5000/xxx:latest`。

```bash
# 一次就好，之后跟着设备自启
docker run -d --name local-registry --restart unless-stopped \
  -p 5000:5000 -v /DATA/AppData/local-registry:/var/lib/registry registry:2

# 每次重建镜像后推一次
docker tag content-publisher:latest localhost:5000/content-publisher:latest
docker push localhost:5000/content-publisher:latest
```

我原以为要改 Docker 的 daemon 配置、要重启 Docker 才能用明文 HTTP 的仓库 —— 结果不用，`localhost` 的仓库默认就被允许。这个小惊喜让我高兴了一会儿。

推完之后，安装一次成功。

### 坑 3：一个"看起来可写、其实写不进去"的目录

我本想把自己的文件放在 `/DATA/casaos`。权限看着是 `777`，写入测试也通过，`mkdir` 却报"文件已存在"，紧接着 `ls` 又说"没有这个文件"。

后来才知道，那是 ZimaOS 的加密/锁定目录，写入是假象。

**教训：在别人的平台上判断"能不能写"，只能写完再读一次，别信权限位。** 应用数据应该放 `/DATA/AppData/`。

### 坑 4：应用数据目录需要 root 权限建

`/DATA/AppData` 是 root 的，普通用户建不了目录。这一步绕不开 `sudo`。

还有个小细节：设备上 `casaos` 用户的主组**不叫** `casaos`，是 `samba`。所以 `chown casaos:casaos` 会直接报错，只写属主就行。

### 坑 5：这台设备上没有 `timeout` 命令

我习惯性地在命令前加 `timeout 30` 防止卡死，结果设备上根本没有这个命令（busybox 环境）。现在我都改用 `curl -m` 这类自带的超时参数。

### 坑 6：我一开始以为要配置时区

我以为定时发布会因为时区出错，专门研究了一圈 `TZ`。

后来想明白：**排期时间是带着时区偏移的完整 ISO 字符串传递的，解析时如果没有偏移会直接报错，所以根本不会"猜错"**；而定时发布本身是 Shopify 那边的计划，容器用 UTC 也无所谓。`TZ` 的作用只是让日志时间戳好读。

这是个典型的"看起来是坑，其实是自己想多了"。

### 坑 7：面板应用的元数据有三个硬要求

ZimaOS 的面板应用需要一段 `x-casaos` 元数据（图标、标题、端口、分类）。我第一版有三个地方写错：

| 字段 | 要求 | 我错在哪 |
|---|---|---|
| `port_map` | 必须是**字符串** | 我写成了数字 |
| `main` | 必须**对应 services 里的键名** | 我写的名字和 service 名不一致 |
| `icon` | 安装时会被抓取，要是**能公开访问的地址** | 我一开始指向了应用自己的端口 —— 那时容器还没起来 |

还有一条经验：**图标别指向应用自身**。安装的那一刻应用还没跑，图标就抓不到了。最后我把图标放进代码仓库，用仓库的公开地址。

## 现在的样子

一切跑起来之后，我的日常变成了这样：

早上起来，打开浏览器，看一眼排期时间轴 —— 未来两周哪几天有内容、有几篇、分别在哪个栏目，格子式排开。确认无误，关掉。

周六、周日的内容在周五就已经排好了。它们会在我睡觉的时候按点上线。

**我不需要为了"周末断更"这件事守在电脑前了。** 写稿子的时候就专心写稿子，发布这件事交给了工具和那台一直开着的设备。

顺便说，因为这个工具是要面向海外内容的，我还把它做成了中英双语，界面可以整体切成英文 —— 对一个内容工具来说，这也算一种"通用"。

## 给和我一样的小白的几条建议

如果你也在自己动手把项目搬上 NAS：

1. **先把"这东西真的需要 7×24 吗"想清楚。** 我纠结了很久可靠性，最后发现我的核心需求只是"随时能提交"。需求想清楚，方案会简单很多。
2. **镜像职责单一，但服务可以合并。** 前端和后端合成一个容器、一个端口，是新手最省事的选择。
3. **凭据和配置永远不进镜像。** 环境变量给凭据，文件挂载给配置。
4. **面板安装失败时，去翻设备日志。** 界面上只有"失败"两个字，日志里才有"为什么"。我那次看到它连试五个镜像源，一下就明白了。
5. **本地镜像仓库是本地镜像的兜底方案。** 尤其是从源码构建、不想把镜像推到公网的场景。
6. **在别人的平台上，写完要读一次。**

## 最后

作为 SEO，我做的事情本质上很朴素：让好内容不断出现在该出现的地方。

而 ZimaOS 帮我解决的，是一个我一直没意识到自己其实需要的东西 —— **一个不需要我操心的"一直在线的入口"**。

它不需要很强，不需要很高深，只要一直开着、能被我随手打开、能把我的内容按计划送出去，就够了。

上周六我睡到了自然醒。醒来看了一眼排期，内容已经上线了。

这就是我想写下来的原因。
